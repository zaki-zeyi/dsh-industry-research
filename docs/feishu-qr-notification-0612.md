# 0.6.12 二维码路径兼容与通知接收人修复

## 二维码路径验证

对本机 Lark CLI 1.0.98 使用同一个测试 URL，在新建的临时工作目录内分别传入绝对输出路径和 `./relative.png`，两次均退出码 0，文件实际生成。本机未复现“绝对路径一律被拒绝”的现象；不能以此推断其他系统或更严格 CLI 版本也接受绝对路径。

应用登记和个人授权两个二维码入口均改用 `--output ./qrcode.png` 并设置临时目录为 cwd。服务端依旧使用临时目录中的绝对路径读取 PNG。测试使用虚构 URL，不发起 OAuth 登录、不修改真实凭据；诊断生成文件已清理。

## 本次通知异常

只读检查用户本地任务数据库发现，失败历史日报没有 `notificationRecipient`，仅保存了原应用及原账号快照，诊断只有通用 retry。通知代码在发起 IM 请求前就会拒绝缺失接收人的任务，原错误转换又没有保留这一原因。

同时发现 release 基线的绑定 status 没有返回已验证用户的 openId，而任务创建逻辑依赖该字段保存接收人。这会导致新日报/周报或内部资料任务继续缺少接收人，现已恢复字段返回。

只读身份验证显示，目标历史任务原应用的个人身份和机器人身份均可验证；当前绑定已经换成其他应用。不同应用下的 openId 不能直接混用。未实际发送消息，身份验证成功不能证明机器人发送权限和接收范围已全部通过。

## 修复边界

- 新任务从已验证的绑定状态保存 notificationRecipient。
- 历史任务重试时，先验证当前应用仍为任务原应用，再验证任务原账号快照与 CLI 个人身份一致、机器人身份可用；只有这些条件满足，才允许恢复缺失接收人。已有接收人和原有幂等键不改变。
- 无账号快照、账号未验证或应用已切换时，不猜测收件人，不迁移给新账号。分别显示 MISSING_RECIPIENT / RECIPIENT_UNVERIFIED / USER_AUTH_UNAVAILABLE / BINDING_CHANGED。
- 发送前失败与真实 IM 请求失败分阶段记录；应用不一致时记录原应用与当前应用 ID，不记录个人 openId、令牌或消息正文。
- 应用登记包含独立 tenant 权限 `im:message:send_as_bot`；修复机器人权限时锁定当前 App ID，不更换应用，保留原个人身份。修复后只重新检查绑定状态，仍正常时补发通知，不为机器人权限修复而重新发起个人登录。用户授权若确实失效，界面单独提示个人授权问题。
- 未修改用户真实数据库、未更改账号授权，未自动发送测试消息。历史任务若仍绑定旧应用，需要用户恢复原绑定再点击重试，或者在当前应用下生成新报告。
