# 平台日志与飞书连接监测（0.6.10）

入口位于工作台顶部“设置飞书根目录”右侧的“平台日志”按钮。平台日志包含“运行日志”和“飞书连接监测”两个子栏目，侧栏不再单独显示日志入口。

## 使用

1. 打开右上角“平台日志”，选择“飞书连接监测”子栏目，点击“立即检测连接”。
2. 如果绑定失败，重新执行绑定后再次查看监测记录。日志按应用登记、本机凭据保存、二维码生成、个人授权发起/确认、绑定结果校验分阶段记录。
3. 可以筛选错误/提醒/信息，暂停自动刷新后加载更早记录，或导出当前已加载的记录及最近一次检测结果。

打开窗口时默认每 5 秒刷新日志，不重复调用飞书验证接口。主动检测只调用当前 profile 的 `auth status --json --verify`；不修改绑定、不重新登录、不发送测试消息。机器人身份通过不代表发送消息权限、发布状态或接收范围已通过真实验收。

## 诊断字段

结构化日志含事件、阶段、分类错误码、耗时、应用 ID、profile 和关联编号。应用登记返回成功与本机保存成功分别记录，可定位“飞书成功但本机保存失败”。不会持久化原始 CLI stdout/stderr、密钥、令牌、设备码、二维码链接、用户标识或消息正文。未知异常使用 `UNKNOWN_ERROR`，不根据通用提示猜测底层原因。

日志复用本地 `runtime_logs` 表，平台共保留最近 1000 条，重启后仍可查看。过滤在数据库分页前执行。监测写入失败不会阻断原连接操作。采集通过插件内的 `FeishuBinding` CLI 和 SDK 调用，其他进程或 Agent 自行执行的 CLI 不在采集范围内。

## 当前基线与验证范围

飞书连接核心以 `origin/release@59371f1` 为基线，在外围加入观测层。0.6.9 移植 `merge02-04@4811d52` 的凭据更新修复：同一所选应用直接 `config init --name` 更新原 profile；其他已有应用遇到重复 App ID 时，读取 profile 列表并更新对应配置。扫码与手动配置共用此逻辑。密钥仅通过 stdin 传入，不删除 profile、不切换 CLI 默认选择；保存失败不提交新的应用选择。预期的首次重复创建可能留下 `PROFILE_CONFLICT` 记录，需要结合随后的凭据更新成功记录判断恢复结果。

原有新版测试中涉及自动重试、Bearer 兼容登录和账号切换事务的预期不适用于恢复后的 release 基线，仍保留这些测试以显示差异，不把它们删除或标为已通过。本次验证使用隔离数据库、模拟 CLI/SDK 和浏览器接口；未在用户真实飞书环境完成扫码或机器人发送验收。

0.6.10 补齐 `merge02-04` 的 Windows CLI 启动修复，绑定服务通过 `larkLaunch` 定位用户 `.local/bin`、PATH 或 npm 安装目录中的原生 exe，并支持显式无扩展路径补全 exe。CLI 错误的 stdout/stderr 仅供内存内分类和重复 profile 识别，日志仍只存白名单诊断字段。开发环境实测原版直接执行 `lark-cli --version` 返回 `ENOENT`，原生启动方式成功返回版本 1.0.98；改用原生启动后，开发环境本机默认 CLI profile 的只读身份验证通过。这不等同于安装后用户所选 profile 或机器人发消息已验收。
